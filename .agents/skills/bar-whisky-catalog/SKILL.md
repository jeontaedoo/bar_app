# 로컬 위스키 데이터 관리

먼저 변경 대상을 구분한다.

- 서버 카탈로그: `server/data/whiskies.json`, `server/data/tags.json`, `server/sheets/utils/whiskeyProject.ts`
- 클라이언트 분류·검색 데이터: `app/sheets/whiskySheet.ts`의 카테고리와 한영 검색 별칭

서버 카탈로그의 구조나 출처를 변경하기 전에 `server/data/README.md`를 확인한다.

## 서버 카탈로그

- 각 파일 안에서 `pk`가 중복되지 않도록 한다. 위스키의 `tags` 값은 태그 `pk`를, `comparable` 값은 위스키 `pk`를 참조해야 한다.
- 태그 ID는 `whiskies[].tags`에 두고, 태그 이름은 `tags.json`에서 관리한다. 특별한 필요가 없으면 별도 `tagtracker` 데이터를 다시 만들거나 위스키마다 태그 이름을 중복 저장하지 않는다.
- 세부 종류를 분류할 때는 확인 가능한 출처를 사용하고 불확실성을 남긴다. 스코틀랜드 지역 정보만으로 싱글몰트나 싱글그레인이라고 단정하지 않는다.
- 설명이 없는 경우 내용을 만들어 넣지 말고 API와 화면에서 선택 항목으로 처리한다. 요청이 없다면 제거된 가격, 생성 시각, 태그 빈도 필드를 되살리지 않는다.
- WhiskeyProject 데이터와 이미지 URL은 재사용 권한이 확인되지 않은 테스트 자료로 취급한다. 공개 배포나 새 데이터 출처 도입 전에 이용 조건과 사용자 요청 범위를 확인한다.
- JSON만 바꿨더라도 `server/sheets/utils/whiskeyProject.ts`의 변환 결과와 영향을 받는 `/api/whisky/whiskey-project` 응답 형태를 확인한다.

## 클라이언트 분류·검색 데이터

- `WHISKEY_CATEGORIES`의 `id`는 페이지 라우트와 필터 값으로 사용되므로 기존 링크와 조회 로직을 확인한 뒤 변경한다.
- 카테고리 이름과 설명은 원산지와 세부 종류를 혼동하지 않게 작성한다. 지역 정보만으로 싱글몰트·싱글그레인 등 제조 방식을 추정하지 않는다.
- `WHISKY_ALIASES`는 실제 검색 대상의 영문 표기와 맞춰 관리한다. 같은 한글 키의 중복, 잘못된 브랜드 연결과 도달 불가능한 별칭을 확인한다.
- 데이터 모양을 바꾸면 이를 읽는 페이지와 composable의 타입 및 필터 로직을 같은 변경에서 갱신한다.

## 검증

서버 카탈로그는 레코드 수, 중복 `pk`, 파일 간 참조와 제거된 키의 재등장 여부를 검사한다. 클라이언트 분류·검색 데이터는 중복 ID, 라우트 연결과 별칭 검색 결과를 확인한다. 수정 후 `npm run build`를 실행하고 분류하거나 연결하지 못한 항목을 보고한다.
